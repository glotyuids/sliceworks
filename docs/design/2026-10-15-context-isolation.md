# Make worker context isolation structural, not advisory

Dated design note, frozen. Written 2026-10-15 on the branch `codex-runtime`.

Question from the owner: how does sliceworks stop the coordinator's conversation from flowing into implementers, reviewers, analysts and researchers on both Claude Code and Codex; what else reaches a worker besides that history; what is known about the cost and quality effects; and which changes would make isolation a property of the runtime rather than of the coordinator's good behaviour? Scope: the plugin as it stands in the uncommitted 0.8.0 work (`scripts/runtimes/codex/dispatch.sh`, `agents.py`, the hook normalisation in `hooks/lib.sh`, the Claude Code dispatch through named plugin subagents). This note proposes; it changes nothing.

**The short answer.** Both runtimes start a named worker fresh by default, and both have a fork path that copies the whole parent conversation. On Claude Code the fork path is **on by default in every interactive session since v2.1.232**, and the coordinator model chooses it by asking for `subagent_type: "fork"`. On Codex the newer multi-agent tool (`MultiAgentV2`) **forks the full history whenever `fork_turns` is omitted**, and no configuration key changes that default. So today's isolation rests on the coordinator choosing well and on writing a one-line prompt, which makes it advisory. Codex implementers and reviewers are already isolated structurally, because `dispatch.sh` starts them as separate `codex exec` processes. History is not the only leak, and on a fresh worker it is not the largest. Every worker also reloads the instruction-file hierarchy (on Claude Code that includes the owner's private `~/.claude/CLAUDE.md`), the skill listing, every inherited MCP tool schema and any text a hook injects. Under Codex, our own SessionStart hook currently tells every worker process to "act as the coordinator". The evidence on quality is consistent but thin: one preprint, one vendor report and one long-context study. The evidence on cost is strong for tool schemas and instruction files. The recommendation has four phases plus a fallback. First, close the free gaps in configuration on this branch. Next, add one spawn guard that both runtimes run, which denies forks and rewrites each dispatch prompt to the canonical line from the committed allocation record. Then trim the channels other than history, role by role, and finally measure each worker's first-turn context so that a runtime update which changes a default shows up as a number. A worker-process launcher for Claude Code is held in reserve in case the hooks cannot do the job.

## How to read the evidence

Every claim below is labelled. **[source]** means read in code at a pinned commit: openai/codex `97ebf2d` on `main`, fetched 2026-10-15. The latest stable release at that date is `rust-v0.162.1`. **[docs]** means official vendor documentation fetched on 2026-10-15: code.claude.com for Claude Code (version markers up to about v2.1.299), and learn.chatgpt.com for Codex. **[secondhand]** means a GitHub issue, a third-party guide, a preprint or a vendor engineering post that reports its own internal measurement. **[inference]** marks our reading where no source states the point directly. Wherever a version boundary matters, it is given, because two of the Codex facts below changed within the last ten days.

## Two runtimes, opposite defaults, one shared fork path

### Claude Code: fresh by default, but the fork is one argument away

**[docs]** A non-fork subagent "starts with a fresh, isolated context window" and "doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read". The only parent content it receives is the Agent tool's prompt string ([Subagents](https://code.claude.com/docs/en/sub-agents); [SDK subagents](https://code.claude.com/docs/en/agent-sdk/subagents)). A fork is the exception. It "sees the same system prompt, tools, model, and message history as the main session", it skips both tool filters, and it shares the parent's prompt cache. Fork mode is **on by default in interactive sessions from v2.1.232** and off in `-p` and the Agent SDK. `CLAUDE_CODE_FORK_SUBAGENT=0` turns it off everywhere, and a permission rule denying `Agent(fork)` keeps the mode but stops Claude from spawning forks ([Subagents](https://code.claude.com/docs/en/sub-agents)). Two other worker forms behave differently. A resumed subagent carries its own earlier history, which is what the method intends for `FINDINGS` and the delta review. An agent-teams teammate gets the spawn prompt but no lead history, and it reloads CLAUDE.md, MCP and skills while ignoring the definition's `skills` ([Agent teams](https://code.claude.com/docs/en/agent-teams)).

Our adopted settings already set `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=0` and a spawn depth of two (`templates/settings.fragment.json`). They do nothing about forks. The dispatch path therefore depends on the coordinator naming `sliceworks:slice-implementer` instead of `fork`, and on it writing one line rather than a summary of the session. The docs say plainly that Claude "composes a delegation message that summarizes the task". **[inference]** That composed message is a second leak path even when no fork happens, and today nothing checks its length or content. The docs do not say what `agent_type` a fork reports in its own hook events. A fork spawned in place of an implementer could therefore escape the role guard, which keys on `agent_type`, as well as inheriting the full tool pool.

### Codex: two tool generations with opposite defaults

**[source]** Two versions of `spawn_agent` coexist. V1 takes a boolean `fork_context`, which serde defaults to `false`, so an omitted value gives a fresh child. V2 takes a string `fork_turns`, and an empty or omitted value becomes `"all"`, a full-history fork ([multi_agents_spec.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/tools/handlers/multi_agents_spec.rs#L649-L684); [v2 spawn.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs#L214-L240)). The version a session gets is decided in this order. `features.multi_agent_v2` wins first. Then `agents.enabled = false` disables multi-agent tools. Then the **remote model catalog's per-model `multi_agent_version`** decides, and V1 is the fallback ([config/mod.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/config/mod.rs)). The same coordinator prompt can therefore produce a fresh child on one model and a full fork on another, and the user cannot see which from the configuration. **No config key sets a fork default or forbids forking.** The request for `[agents] default_fork_turns` (#51032, opened 2026-10-05) and the earlier kill-switch request (#14981) are both open with no maintainer reply ([#51032](https://github.com/openai/codex/issues/51032); [#14981](https://github.com/openai/codex/issues/14981)).

Two recent changes matter for any guidance we write. **[source]** PR #51329, first shipped in `0.162.0`, removed partial forks. A legacy numeric `fork_turns` such as `"3"` is now **silently treated as a full fork**, so older advice to pass `fork_turns: "1"` now *increases* inherited context ([PR #51329](https://github.com/openai/codex/pull/51329)). PR #52241 makes children keep the spawning turn's selected skills and plugins "whether `fork_turns` is `none` or `all`". It is not in `0.162.1` and is present in `0.163.0-alpha.11` ([PR #52241](https://github.com/openai/codex/pull/52241)). A full fork drops reasoning, tool calls and their outputs. It keeps system, developer and user messages and final answers, and it scrubs the parent's multi-agent role hints and guardian approvals ([spawn.rs L83-162](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/agent/control/spawn.rs#L83-L162)). That makes a fork smaller than the raw transcript, but it is still the coordinator's whole decision trail.

The 0.8.0 adapter already avoids the worst case. `dispatch.sh` starts implementers and reviewers as `codex exec` processes, and **[source]** a new exec thread has no parent conversation by construction ([exec/src/cli.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/exec/src/cli.rs)). The prompt it builds puts the role profile first and one dispatch line last, so each worker's prompt starts with a prefix that is stable for its role. The remaining exposure is the native helpers that `agents.py` renders into `.codex/agents/`: the analysts, the explorer, the researcher and, notably, **both reviewers**. A coordinator that spawns the native `code-reviewer` on a V2 model without `fork_turns: "none"` hands it the coordinator's full history. That is exactly the reviewer independence the method forbids breaking.

| Worker form | Gets the coordinator's history? | Who decides |
|---|---|---|
| Claude Code named plugin subagent | No | runtime |
| Claude Code fork (`subagent_type: "fork"`, `/subtask`) | Yes, all of it, plus the full tool pool | coordinator model; settings can forbid it |
| Claude Code resumed subagent (`SendMessage`) | No, only its own earlier history | runtime |
| Claude Code teammate (teams on, named call) | No, but it reloads project context and ignores `skills` | runtime; teams are off in our fragment |
| Codex native child, V1 tools | Only when `fork_context: true` | coordinator model |
| Codex native child, V2 tools | **Yes, unless `fork_turns: "none"`** | coordinator model; no config key |
| Codex `codex exec` worker (`dispatch.sh`) | No | process boundary |
| Codex `codex exec resume <thread>` | Only its own thread | process boundary |

## Codex hooks do carry agent identity inside native subagents

The adapter document (`scripts/runtimes/codex/README.md`) says Codex "passes `agent_type` on `SubagentStart` and `SubagentStop` only, never on `PreToolUse`". It lists "native subagents are not guarded by role" as a known limit. The source says otherwise. **[source]** `PreToolUseCommandInput` has optional `agent_id` and `agent_type` fields, and so do PostToolUse, PermissionRequest, PreCompact and PostCompact ([hooks/src/schema.rs L278-381](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/hooks/src/schema.rs#L278)). They are filled only for thread-spawned subagents (`SessionSource::SubAgent(ThreadSpawn)`), with `agent_id` set to the child's thread id and `agent_type` set to the role name, or **`"default"` when the spawn named no role**. Internal subagents such as the guardian skip hooks ([hook_runtime.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/hook_runtime.rs#L1059)). Because the child's Config is a clone of the parent's, the same hooks fire inside it. **[docs]** The hooks page documents the SubagentStart and SubagentStop matchers on `agent_type`, and says that "subagent hooks use the parent session id". It does not list the identity fields under PreToolUse ([Hooks](https://learn.chatgpt.com/docs/hooks.md)). The page is incomplete, not contradictory, and the adapter's sentence over-read it.

The resolution: on Codex `main`, a PreToolUse event inside a native child names that child's role. The release that first shipped this is not established, so it must be verified on the installed CLI. Even so, the adapter has to change in three places. First, the README's identity row and first known limit should say that native children are identified by `agent_type` where the installed version sends it, and that the role guard then applies to them, with no code change, because `sw_agent_type` already reads `.agent_type` first. Second, `sw_agent_type` has a regression waiting to happen. Inside a `dispatch.sh` implementer, a role-less native child reports `agent_type: "default"`. That non-empty value now wins over `SW_ROLE`, and `hooks/role-guard.sh` lets an unknown type through unguarded. The child inherits the implementer's `workspace-write` sandbox, including the main checkout's `.git` as a writable root, so it would write without the implementer's guard. The fix is to treat `"default"` as no identity and fall through to `SW_ROLE` and then the worktree marker. Third, the worker *process* itself is a root session and carries no `agent_type`, so `SW_ROLE` and the marker remain necessary there. Two limits keep the hooks a backstop rather than the boundary. The Codex docs themselves call tool hooks "a useful guardrail, not a complete enforcement boundary". And a native child of the coordinator inherits the coordinator's sandbox. Implementers and reviewers therefore stay processes even after this correction.

## Eight channels besides history reach every worker

A worker that never sees one turn of the coordinator's chat still starts with a substantial context, and most of it is chosen by configuration rather than by the brief.

| Channel | Claude Code named subagent | Codex native child | Codex `exec` worker | Lever |
|---|---|---|---|---|
| Instruction files | full CLAUDE.md hierarchy including `~/.claude/CLAUDE.md`, `CLAUDE.local.md`, unscoped project rules and AGENTS.md | parent's applied AGENTS.md snapshot, project instructions reloaded at the parent's cwd | AGENTS.md chain at the worktree; user config unless `--ignore-user-config` | `omitClaudeMd: true` (v2.1.271+); Codex `project_doc_max_bytes` |
| Base and developer instructions | own profile body plus environment details | **parent's base instructions**; role `developer_instructions` | Codex base prompt plus our profile as the prompt | role files |
| Skill listing and bodies | listing reminder; Skill tool stays usable; `skills:` bodies preloaded | inherited from parent (and selected skills since #52241) | discovered skills | Codex `skills.include_instructions = false`, `skills.bundled.enabled = false` |
| MCP tool schemas | parent's MCP tools after filters | **all of the parent's MCP servers; a role cannot remove them** | servers in user and project config | Claude `tools` / `disallowedTools: mcp__*`; Codex: none per role |
| Hook-injected text | plugin hooks fire inside; SubagentStart `additionalContext` | hooks cloned with Config; SubagentStart context | **our SessionStart hook fires** | hook bodies |
| Memory | parent auto memory not loaded; `memory:` loads the agent's own | `[memories]` settings follow the parent (content injection untraced) | as configured | Codex `features.memories = false` |
| Snapshots and rosters | git status snapshot; sibling roster when `SendMessage` is present | V2 usage hint ("All agents share the same directory") | none beyond the environment | — |
| Repository files | anything readable in the worktree | anything readable at the parent's cwd | anything readable; the read-only sandbox still reads | filesystem scoping only |

Sources: Claude Code from [Subagents](https://code.claude.com/docs/en/sub-agents) and [Context window](https://code.claude.com/docs/en/context-window) **[docs]**; Codex native children from [child_config.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/agent/child_config.rs#L132), [agents_md_manager.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/agents_md_manager.rs#L28) and [role.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/agent/role.rs#L69) **[source]**, and the Codex [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md) page **[docs]**. Since PR #39299 (2026-08-18), a Codex role file can only *reduce* capabilities. Of everything it might set, Codex copies only the instructions, model, effort, verbosity and personality fields. It honours `false` for `shell_tool`, `apps`, `plugins`, `memories` and `request_permissions_tool`, and it **ignores** `sandbox_mode`, `approval_policy`, `model_provider` and `mcp_servers` ([PR #39299](https://github.com/openai/codex/pull/39299)). Third-party guides that show those keys in agent files predate that PR.

Three of these channels are specific to sliceworks. The first is our own hook. `hooks/session-context.sh` runs on SessionStart for `startup|resume|compact` and prints a paragraph that begins "To act as the coordinator read START.md first". **[source]** Codex runs SessionStart hooks under `codex exec` (the exec test suite exercises exactly that, [exec/tests/suite/hooks.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/exec/tests/suite/hooks.rs)). Every trusted `dispatch.sh` worker therefore opens with coordinator instructions, in front of its role profile. On Claude Code the docs do not say whether SessionStart fires again for a subagent; the separate SubagentStart event suggests it does not. The second is the owner's global instruction file. A Claude Code subagent loads `~/.claude/CLAUDE.md`, so personal, cross-project instructions reach implementers and reviewers in every adopted project. The third is the rules file. `adopt` writes the rules for every agent to `.claude/rules/sliceworks.md` (about 2 KB), and those rules arrive through the same CLAUDE.md channel. That matters below, because switching that channel off also switches the rules off.

Repository files are the last channel, and hooks cannot close it. **[inference]** A dispatch rule controls what the coordinator *asks* a worker to read, not what the worker *can* read. A reviewer in a worktree can open the implementer's committed handoff, the commit messages and `PROGRESS.md`. Isolation of knowledge, as distinct from isolation of conversation, needs either filesystem scoping or a profile rule about what to read first. Only the first is structural.

## What the numbers say about cost and quality

The cost side is the better measured of the two. Anthropic measured tool definitions at about **26K tokens for GitHub's 35 MCP tools**, about **55K for five common servers (58 tools)**, and up to 134K internally before optimisation. With 50+ tools, deferred loading through tool search cut the pre-work context from about 77K to 8.7K tokens (-85%), and it *raised* MCP-eval accuracy, from 49% to 74% on Opus 4 ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use), **[secondhand]**, vendor-measured). Claude Code now defers MCP schemas by default ([Context window](https://code.claude.com/docs/en/context-window), **[docs]**). The same docs give an illustrative start-up inventory, not a guarantee: system prompt about 4,200 tokens, project CLAUDE.md about 1,800, user CLAUDE.md about 320, skill descriptions about 450, environment about 280. They also state that a subagent's own copy of CLAUDE.md "counts against the subagent's context". For instruction files, one controlled study ran SWE-bench Lite (300 tasks) and AGENTbench (138 tasks) on Claude Code with Sonnet 4.5 and on Codex with GPT-5.2. It found that LLM-generated context files changed success by about **-3%** while raising cost by **20-23%**. Developer-written files raised success by about +4% on average, **but not for Claude Code**, and raised cost by up to 19% ([Gloaguen et al., arXiv 2602.11988](https://arxiv.org/html/2602.11988v1), **[secondhand]**, ICLR 2026). Every line a worker inherits is paid once per spawn, and it also steers the worker: agents used `uv` 1.6 times per instance when the file mentioned it, against under 0.01 when it did not.

History is a cost multiplier when a fork does not reuse the cache. **[docs]** A fork's first request reads the parent's cache, because the prefixes are identical. A fresh subagent's first request does not ([Prompt caching](https://code.claude.com/docs/en/prompt-caching)). Subagents and teammates fall in a five-minute TTL bucket by default, and our settings fragment already raises it with `subagentPromptCacheTtl: "1h"`. **[inference]** With caching, forking a 100K-token coordinator can cost about as much on turn one as a fresh 10-20K-token worker. But the fork carries the 100K on every later turn, at cached-read rates, and a slice implementer runs for up to 250 turns. On Codex the cache does not reliably survive the fork. **[secondhand]** One open issue reports first inputs of about 273K tokens, about 24M tokens consumed and **81.9% cache misses** with three subagents at `fork_turns = all`. The reporter ran Codex 0.157.1 against a custom Responses provider ([#53752](https://github.com/openai/codex/issues/53752)). Another reports 74 subagents at depth three and **5.39 billion recorded tokens, 4.98 billion of them from subagents** ([#38989](https://github.com/openai/codex/issues/38989)). A third documents forked subagents losing prompt-cache lineage ([#24704](https://github.com/openai/codex/issues/24704)). `multi_agent_v2.preserve_fork_prefix`, which keeps the cached prefix, exists but defaults to false **[source]**. Anthropic's own multi-agent research system used about **15 times** the tokens of a chat. Its isolated design beat a single agent by 90.2% on an internal research eval, and Anthropic names most coding tasks as "not a good fit" for parallel agents with shared dependencies ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system), **[secondhand]**).

The quality side is consistent but rests on thin direct evidence. The closest test of the method's rule is a single-author preprint: 30 artifacts, 5 injected errors each, Claude Opus 4.6 run through the Claude Code Agent tool, 360 reviews. A **fresh session given only the artifact** scored F1 28.6%. Self-review in the producing session scored 24.6%, a subagent given the generation prompt plus the artifact 23.8%, and a second same-session review 21.7%. On critical errors the fresh session caught 40% against 29-31% for the others (p=0.008 against self-review, d=0.52) ([arXiv 2603.12123](https://arxiv.org/html/2603.12123v1), **[secondhand]**). It is one model with injected errors, plus a language confound. The subagent result suggests that even the *generation prompt* anchors a reviewer, but that difference was not significant. Cognition, which argued in 2025 for sharing full traces, reported in April 2026 that review works best "when the coding and review agents do not share any context beforehand", with no number attached. It also reported that writes should stay single-threaded and that the coder, who holds the decisions, should filter the reviewer's findings ([Multi-agents: what's actually working](https://cognition.com/blog/multi-agents-working), **[secondhand]**). The method already prescribes both of those. Persuasive author narrative is an attack surface. An iterative attack that biased PR metadata got vulnerable code past Claude Code and CodeRabbit review pipelines in **32 of 33 CVE cases** ([arXiv 2603.18740](https://arxiv.org/abs/2603.18740), **[secondhand]**). Inherited history also behaves as distractor text. Across 18 models, focused prompts of about 300 tokens beat full prompts of about 113K tokens on LongMemEval for every model family ([Chroma, context rot](https://www.trychroma.com/research/context-rot), **[secondhand]**).

Isolation is not free of risk, and the strongest counter-argument deserves a direct answer. Cognition's 2025 case is that actions carry implicit decisions, so isolated parallel writers diverge ([Don't build multi-agents](https://cognition.com/blog/dont-build-multi-agents)). Google's scaling study measured error amplification of **17.2x for independent agents** that aggregate only at the end, against **4.4x for a centralised hub** that validates. Every multi-agent variant tested lost 39-70% on sequential reasoning ([Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/), **[secondhand]**). Sliceworks is the centralised case. Implicit decisions are made explicit before dispatch, as frozen contracts, D entries and a brief of at most 150 lines. Writers are single per slice. Every candidate passes T1, a fresh reviewer and T2 before it counts. The remedy the evidence supports is a better brief, not a forked history: Anthropic's failed subagents had vague one-sentence tasks, and its fix was a structured brief with objective, format, tools and boundaries ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). **No published study compares a coding implementer given a forked history with one given a minimal brief on both cost and success.** Phase 3 below exists partly so that sliceworks can produce its own number.

## Four ways to get isolation, ranked by what they guarantee

| Option | What guarantees the worker's start | Claude Code | Codex | Main costs |
|---|---|---|---|---|
| A. One-line prompt and named agents (today on Claude Code) | the coordinator's choices | fresh unless it forks | fresh only on V1 or with `"none"` | advisory; nothing checks it |
| B. Settings that forbid forks | the permission system | `CLAUDE_CODE_FORK_SUBAGENT=0`, `Agent(fork)` deny | **not available** (no config key) | Claude only; also blocks the owner's `/subtask` in adopted projects |
| C. A spawn guard hook (deny, rewrite) | a trusted hook on every spawn | deny forks; rewrite the prompt via `updatedInput` (rewrite of Agent input inferred, verify) | rewrite to `fork_turns: "none"` / `fork_context: false` **[source]** | hooks fail open on timeout; Codex calls them a guardrail; Codex needs hook trust |
| D. A separate process per worker | the process boundary | `claude -p` launcher (not built) | `dispatch.sh` (built) | a second observability surface; approvals outside the host UI; no fork-cache savings |
| E. An MCP dispatcher with MCP tasks | the process boundary, portable | as D | as D | tasks are experimental and client support is unverified; the server runs outside every sandbox |

Option D is the strongest guarantee and is already in place where it was needed most: Codex writers and reviewers. Option E adds nothing that D does not already give sliceworks, because `dispatch.sh` is already a launcher both runtimes can call through their shell. The removal of `codex mcp-server` on 2026-09-05 ([PR #42993](https://github.com/openai/codex/pull/42993)) closes the old route anyway. Claude Code is different. A worker process there loses the completion notifications and in-session permission prompts that the method relies on. The documented minimal mode, `--bare`, reads no OAuth or keychain credentials and needs an API key ([CLI reference](https://code.claude.com/docs/en/cli-reference), **[docs]**), which conflicts with a run budgeted against plan usage. On Claude Code the right backbone is therefore B plus C: named in-session subagents, with forks forbidden by settings and every spawn checked and rewritten by a hook. D stays a fallback.

## Phased recommendation

### Phase 0: correct the record and close the free gaps (this branch, before 0.8.0 ships)

**Change.** Rewrite the Codex adapter's identity row and first two known limits to say four things: PreToolUse carries `agent_type` inside thread-spawned children on Codex `main`; the role guard covers named native roles where the installed version sends it; V2 forks by default; and numeric `fork_turns` means "all" since 0.162.0. Add `"CLAUDE_CODE_FORK_SUBAGENT": "0"` to the settings fragment's `env`, and `"Agent(fork)"` to its `permissions.deny`. Make `sw_agent_type` treat `agent_type == "default"` as no identity, falling through to `SW_ROLE` and the worktree marker. Make `session-context.sh` print nothing for the coordinator when a role is set, and print instead a two-sentence worker paragraph: role, allocation id from `SW_ALLOCATION`, and "read the files your dispatch line names; you are not the coordinator". **Files.** `scripts/runtimes/codex/README.md`, `templates/settings.fragment.json`, `skills/adopt/SKILL.md` (the merge list names the new keys), `hooks/lib.sh`, `hooks/session-context.sh`, `tests/test_hooks.sh`, `CHANGELOG.md`. **Guarantees.** In adopted Claude Code projects the permission system, not the model, refuses fork spawns. Codex workers no longer open with coordinator instructions. A role-less native child of a Codex implementer stays under the implementer's guard. **Verify on installed CLIs.** On Claude Code (interactive, v2.1.232 or later): an `Agent` call with `subagent_type: "fork"` is refused under the deny rule, and `/subtask` behaviour is acceptable to the owner. On Codex (`codex --version` recorded): a logging hook shows that SessionStart fires in a `dispatch.sh` worker, that the hook process sees `SW_ROLE`, and that PreToolUse inside a native child carries `agent_type` (role name or `"default"`).

### Phase 1: one spawn guard for both runtimes (0.9.0)

**Change.** Add a new PreToolUse hook on the `Agent` matcher, which Codex also matches for `spawn_agent`. On Claude Code it does three things. It denies `subagent_type: "fork"`, as defence in depth if a user setting re-enables forks. It denies a `name` argument while agent teams are enabled. For the sliceworks writer and reviewer roles, it requires an allocation id in the prompt and checks that the allocation record exists, is committed and names the same role. It then replaces the prompt through `updatedInput` with the canonical dispatch line built from that record, echoing every other field unchanged. Other roles get a byte cap on the prompt (`SW_DISPATCH_PROMPT_MAX`, default 1,500). On Codex the hook does three things. It denies a native spawn of `slice-implementer`, `code-reviewer` or `named-risk-reviewer`, which must go through `dispatch.sh`. For every other spawn, it detects V2 by the presence of `task_name` and returns `allow` with the original arguments plus `fork_turns: "none"`; on V1 it returns them with `fork_context: false`. And it never adds keys, because V2 arguments use `deny_unknown_fields`, and it never touches the `message` field, which is schema-marked encrypted ([v2 spawn.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs); [registry.rs](https://github.com/openai/codex/blob/97ebf2d94d62e2ff2045f3ea17b6e11eae9a21fb/codex-rs/core/src/tools/registry.rs#L701)). That last rule has one consequence for `lib.sh`. `sw_normalize` currently rewrites `$input` and adds `subagent_type`, so it must keep the raw input in a separate variable from which the hook builds `updatedInput`. Move the dispatch-line builder out of `dispatch.sh` into one script that both the hook and `dispatch.sh` call, so the two runtimes send byte-identical lines. Have `agents.py` stop rendering the two reviewers as native Codex agents. **Files.** `hooks/spawn-guard.sh` (new), `hooks/hooks.json`, `hooks/lib.sh`, a shared line builder under `scripts/` (new), `scripts/runtimes/codex/dispatch.sh`, `scripts/runtimes/codex/agents.py`, `scripts/runtimes/codex/README.md`, `method/10-autonomous-operation.md` (one sentence under "Two runtimes": the dispatch line is built from the committed allocation record by a script, never written by a model), `tests/test_hooks.sh`, `tests/test_codex_runtime.py`, `CHANGELOG.md`. **Guarantees.** On both runtimes, a worker's task message is the committed allocation's line, whatever the coordinator typed. On Codex, every spawn the hook sees starts without parent history, whichever tool version the model catalog selected. The limits are those of the hook layer: Claude Code lets a timed-out hook through ([Hooks](https://code.claude.com/docs/en/hooks)), and Codex runs a plugin hook only once its hash is trusted. **Verify on installed CLIs.** On Claude Code: the hook's `tool_input` for `Agent` contains `name`, `isolation` and `run_in_background`, not only the four documented fields; an `updatedInput` that replaces `prompt` is honoured (check the first user message in the subagent transcript); a deny on `Agent` surfaces to the coordinator as a readable reason. On Codex: which tool version the configured model receives (inspect the keys of `tool_input`); that PreToolUse fires for `spawn_agent` with the raw arguments; that the rewrite is honoured (the child's rollout begins without parent messages); that `message` survives the round trip; and what happens when the hook errors.

### Phase 2: trim the channels other than history, role by role (0.9.x)

**Change.** On Claude Code, set `omitClaudeMd: true` on `code-reviewer`, `named-risk-reviewer`, `business-analyst`, `system-analyst`, `researcher` and `code-explorer`, mirroring what the built-in Explore and Plan agents already do. The field needs v2.1.271 or later, and older versions ignore unknown fields silently. It is not on the list of fields ignored for plugin agents, but the docs do not confirm the combination. The flag drops the user, project and local CLAUDE.md together, and with them the unscoped `.claude/rules/sliceworks.md`. So add a SubagentStart hook, matched on the scoped role names, that injects the rules file (about 2 KB) as `additionalContext`. Keep CLAUDE.md for the implementer for now: its project conventions are the instruction file the study above found occasionally useful, and its cost is the one Phase 3 measures. Check that every profile's `tools` allow-list keeps MCP tools out, and add `disallowedTools: mcp__*` where it does not. On Codex, render `skills.include_instructions = false`, `skills.bundled.enabled = false` and `features.memories = false` into every role file, and pass the same values as `-c` overrides in `dispatch.sh`. Do **not** add `--ignore-user-config` or `features.plugins = false` until verification shows that plugin enablement and hook trust survive them, because a worker without the plugin's hooks loses the role guard and the T0 stop gate. For reviewers, the dispatch line names the base and head SHAs, the brief, the contract and the T1 log, and does not name the handoff. The profile asks the reviewer to draft its findings before it reads any author narrative. This is a judgment from suggestive evidence (the CCR subagent condition and the framing attack), not a proven effect. **Files.** `agents/*.md` (six profiles), `hooks/worker-context.sh` (new), `hooks/hooks.json`, `scripts/runtimes/codex/agents.py`, `scripts/runtimes/codex/dispatch.sh`, the shared line builder, `agents/code-reviewer.md`, `agents/named-risk-reviewer.md`, `tests/`. **Guarantees.** Reviewers and analysts on Claude Code no longer carry the owner's private instructions or the coordinator-oriented project file. **Change.** Record each worker's first-turn input size, by role and runtime, and flag outliers. ## Conclusion

Isolation in sliceworks has been described as one property, but it is three that fail independently. *History* isolation is the one the question started from, and on both hosts it is a single argument away from failing. *Prompt* isolation, meaning the coordinator's own summary of the task, is unguarded on Claude Code even when no fork happens. *Ambient* isolation covers the instruction files, the skill catalogue, MCP schemas and hook text. It is the largest per-spawn cost, and it is set by configuration the coordinator never sees. One hook and a handful of settings close the first two on both runtimes. The third has to be tuned role by role and measured, because what a reviewer should not see (the owner's private file, the author's narrative) differs from what an implementer still needs (the project's conventions).

The finding with the widest effect is that both vendors are moving defaults under us. In ten days Codex turned numeric partial forks into full forks and made fresh children inherit the parent's skills, and the model catalog, not the user, chooses which spawn semantics a session gets. Any isolation built on today's defaults will drift. That is why the recommendation ends with a measurement rather than a rule. With a per-role first-turn number on the dashboard, the next silent change in a host shows up in sliceworks' own telemetry.
