# The Codex adapter

Method chapter 10 keeps the method independent of the host and puts the rules that differ between hosts in one adapter document per runtime. This is the one for Codex. The skills and the method name Claude Code's mechanisms; under Codex, read each one through the table below. Automated launcher tests use a stand-in CLI. The installed-CLI checks below record what was verified on 2026-10-16 and what remains unverified.

## Mechanism by mechanism

| In the skills and the method | Under Codex |
|---|---|
| The plugin (`.claude-plugin/plugin.json`) | `.codex-plugin/plugin.json`, same name and version (`scripts/release.sh` bumps both); the repository's `.agents/plugins/marketplace.json` lists it. |
| `${CLAUDE_PLUGIN_ROOT}` in a skill | The plugin root: the directory two levels above that `SKILL.md`. Codex substitutes it for hook commands, not inside skill text. |
| Hooks (`hooks/hooks.json`) | The same file. Codex matches `apply_patch` as `Edit` and `Write`, its shell as `Bash`, `spawn_agent` as `Agent`; `hooks/lib.sh` normalises the input (argv commands, patch file lists, `cmd`). Codex runs a plugin's hooks only after they are **reviewed and trusted** (`/hooks` in an interactive session): trust them once before the first dispatch, and again after an update changes them. |
| The role of the acting agent (`agent_type`) | Inside a native subagent, Codex's tool hooks carry `agent_type` (the role name, or `"default"` for a spawn without one) on current `main`; the published hooks page does not list it, so *verify* on the installed version. A worker process is a root session with no `agent_type`: it carries its role in `SW_ROLE` and in the marker `<worktree git dir>/sliceworks-role`, both written by `dispatch.sh`. `sw_agent_type` reads them in that order and treats `"default"` as no role, so a role-less child of a worker keeps the worker's guard. |
| Spawning a read-only helper (explorer, analysts, researcher) | A native Codex subagent by name, from `.codex/agents/<role>.toml`, generated by `agents.py sync`; `agents.py check` is the T0 parity step (method 10, "Two runtimes"). |
| Dispatching the `slice-implementer` (`isolation: worktree`) | `dispatch.sh <allocation-id>`: a detached `codex exec` process in the allocation's worktree, sandbox `workspace-write` with the main checkout's `.git`, `<outputs>` and `<run>` as extra writable roots. Never a native subagent: one shares the coordinator's checkout and sandbox. |
| Spawning `code-reviewer` or `named-risk-reviewer` | `dispatch.sh` on a `mode: review` allocation: sandbox `read-only`, a fresh context. |
| Resuming a worker with `FINDINGS`, a new brief or a `HOLD` answer | `dispatch.sh <allocation-id> --resume "<message>"`: `codex exec resume <thread>` with `-c sandbox_mode="<sandbox>"` (resume has no `-s`); the host supervisor saves the stream's `thread.started` id immediately in `<run>/codex/<allocation>.thread`. |
| The dispatch prompt (`brief` skill, method 7) | Built by `dispatch.sh` from the allocation record: the role's profile, then one line naming the allocation, the brief, the goal condition, the handoff and the return shapes. |
| A completion notification, the wake timer | None arrives. The coordinator's Stop hook continues the turn while workers run (waiting up to `SW_CODEX_WAIT` seconds, default 540) and hands finished workers' first lines over as the next prompt; `collect` reads the evidence. `SW_CODEX_CONTINUE=0` turns the loop off. |
| The T0 gate on an implementer's stop (`SubagentStop`) | The same hook on `Stop` inside the worker process, keyed on `SW_ROLE`; it also runs the pre-handoff command before a HOLD. |
| `run_in_background` (dashboard loop, long tiers) | Start detached: `nohup sh scripts/sliceworks/dashboard-loop.sh 30 >/dev/null 2>&1 &`. A worker runs its own long tiers in the foreground of its process. |
| Following workers | `status.sh`: running and finished worker processes with their return lines, no model turn. |
| Writer cap | `SW_WRITER_CAP` counts live writer processes of `dispatch.sh`; a native subagent thread cap does not apply to them. |
| Usage readings | Read the plan's usage in Codex and record it with `runtime: "codex"`; the budget guard and `dispatch.sh` apply the same holds. |

## Setting up the dual profile

1. Install the plugin from the marketplace (or `scripts/install.sh <project> --tools codex --hooks` for a copy install), restart Codex and trust the hooks.
2. `adopt` writes `.codex/config.toml` from `templates/codex-config.toml` and the `SW_CODEX_*` keys of `.sliceworks/config.env`; set `SW_CODEX_MODEL` and `SW_CODEX_MODEL_STRONG` or leave them empty to inherit.
3. `python3 <plugin>/scripts/runtimes/codex/agents.py sync`, commit `.codex/agents/`, and add `agents.py check` to T0.

## Known limits

- **Native subagents share the coordinator's sandbox.** Where the installed Codex sends `agent_type` in tool hooks, the role guard covers named native roles; on versions that do not, it cannot tell a native subagent from the coordinator. Hooks are a backstop either way, and a native child runs in its parent's sandbox, so writers and reviewers go through `dispatch.sh`.
- **Native subagents can inherit the coordinator's conversation.** The newer `spawn_agent` forks the parent's full history when `fork_turns` is omitted, no configuration changes that default, and since 0.162.0 a numeric `fork_turns` also means all of it. That costs tokens and breaks a reviewer's independence; it is why reviewers run as processes. The fix is planned in `docs/design/2026-10-15-context-isolation.md`.
- **Hook trust.** An untrusted plugin hook does not run. A worker process started before the hooks were trusted runs without the role guard and the stop gate; the sandbox and the merge gates remain.
- End-to-end authenticated `codex exec` and hook-environment inheritance remain unverified here. The worktree marker covers absent `SW_ROLE` inheritance. Installed help confirms resume supports `-o` and `-c`, and does not support `-s`.

## Network boundary and installed-CLI probe

On 2026-10-16 the installed CLI reported `codex-cli 0.162.0-alpha.17.2`. A live `codex sandbox` probe started a host TCP listener on `127.0.0.1` and attempted direct socket connections to that ephemeral port and to external `1.1.1.1:443`. It selected `-P sw-local-probe` and these exact `-c` overrides:

```toml
features.network_proxy = true
permissions.sw-local-probe.extends = ":workspace"
permissions.sw-local-probe.network.enabled = true
permissions.sw-local-probe.network.domains."localhost" = "allow"
permissions.sw-local-probe.network.domains."127.0.0.1" = "allow"
```

The CLI exited 1 before executing the sockets: `unknown variant '0', expected 'allow' or 'deny' in permissions`. Repeating with an isolated `CODEX_HOME` and with `/tmp` as the working directory produced the same parser failure. Neither localhost reachability nor external denial was established. No local-only network mode ships on that evidence. The [official permissions documentation](https://learn.chatgpt.com/docs/permissions) also says domain restrictions need an active proxy; enabling networking alone does not enforce them.

`SW_CODEX_NETWORK` defaults to `0`, its only accepted value. Old `1`, proposed `local`, and all other values are rejected before dispatch. Writers explicitly receive `sandbox_workspace_write.network_access=false`, `approval_policy="never"` and `web_search="disabled"`; `SW_CODEX_EXEC_ARGS` may not override security settings. Do not enable unrestricted networking to make a test pass. This boundary covers writer commands; the CLI itself still needs its model service for inference.

## Host gate protocol

The host launcher automatically services the request while the writer waits. Start the dispatcher outside the worker sandbox. `worker.py` supervises the CLI, captures its thread id, and calls `gate-runner.sh`; the latter refuses a worker role. None of the gate execution needs a model turn. A project with its own dispatcher can invoke `gate-runner.sh <allocation-id>` from its host-side process whenever a request appears, or run it once manually as the coordinator.

1. Run the configured pre-handoff checks first. Commit the slice checkpoint and obtain its full HEAD. Write a temporary JSON file, then rename it atomically to `$SW_CODEX_RUN_DIR/gate-request.json`:

   ```json
   {"request_id":"slice-07-attempt-1","allocation":"alloc-slice-07-r1","slice":"slice-07","head":"<full 40-character commit SHA>","tier":"t1"}
   ```

2. Poll `$SW_CODEX_RUN_DIR/gate-result.json` for the same `request_id` and head. Use a unique request id for each new gate; do not reuse a previous id for different source. The runner consumes a request once and returns the same durable receipt for retries of that id. Only one request may be outstanding for an allocation.
3. Read `result` (`pass`, `fail`, `NOT_RUN`), `exit_code`, `log`, and any `error`. A pass requires exit 0, a last `RESULT=pass` marker, an unchanged HEAD and no tracked source changes. A reused id with different request data is refused. A refusal is never a pass. Per-request log and receipt files remain in the run directory. A pass is evidence for that commit, not permission to merge.

The runner obtains worktree, slice and base from the allocation, checks the repository and HEAD, refuses closed allocations and STOP, allows only implementer T1, and never accepts a command or environment from request data. It runs the **main checkout's** `SW_VERIFY_CMD`, with `--cwd <worktree> --slice <slice> --base <allocation-base> t1`. The project verifier must accept these arguments and **retain its existing verification-slot admission**, including queue fairness and stale-slot recovery. The runner neither creates a competing slot system nor bypasses the verifier's queue. If a project uses different arguments, provide a trusted wrapper as `SW_VERIFY_CMD` that forwards to the existing verifier under that same admission. Do not configure an unrestricted arbitrary-command executor.

The runner holds `<allocation-run>/gate.lock` while a request runs. After an interrupted host process, inspect the active verifier PID/log before clearing a stale lock or `gate-active.json`; never retry a live gate. The broker executes project tests on the host and assumes the configured verifier and assigned slice are trusted development code. It is not a security boundary against malicious test code.

## Writable telemetry and pre-handoff checks

The dispatcher exports these runtime paths (they are derived environment values, not project config keys):

| Environment value | Derived location |
|---|---|
| `SW_CODEX_RUN_DIR` | `<root>/<run>/codex/<allocation>` |
| `SW_METRICS_DIR` | `$SW_CODEX_RUN_DIR/metrics` |
| `SW_TIERS_FILE` | `$SW_METRICS_DIR/tiers.jsonl` |

A project verifier must append tier rows to `${SW_TIERS_FILE:-<state-dir>/metrics/tiers.jsonl}` and route its other worker metric files through `SW_METRICS_DIR` when set. Adapt every hard-coded state append and directory creation, including early failure paths; creating the canonical state metrics directory itself can fail in a writer sandbox. Outputs and the run directory are writable roots; the coordinator state directory is not added. Ordinary coordinator runs can keep canonical paths. `collect.py --root <repo> --merge-worker-metrics` imports complete JSONL object rows into `<state-dir>/metrics/`, under a collector lock and without duplicating previously imported rows. Ordinary collection remains read-only. Only the coordinator runs the merge mode. Imports preserve worker claims; they do not replace review or independently authenticate a pass.

Set `SW_PREHANDOFF_CMD` to lint and every database-free test for the changed packages, including migration registries and other file checks. Empty means `SW_VERIFY_CMD SW_T0_ARGS` (normally T0). Report commands, exit results and logs in the handoff. The implementer Stop gate runs this even with an empty or HOLD `.blocked` marker, then keeps the original T0 gate for candidates. A true BLOCKED return can stop before implementation. A HOLD that cannot run its pre-handoff command must put the exact command in `.blocked` and preserve nonempty output, with `.prehandoff-unavailable.json` containing `command` equal to the configured command and `log` pointing to that output. Remove the exemption and `.blocked` before the next attempt. Budget and STOP escapes remain available.

## Updating a project-local copy from 0.8.0

- Update `hooks/lib.sh` and the six enforcement hook scripts together; `hooks/hooks.json` still names the same entries. Update the implementer profile, the affected skills (`adopt`, `brief`, `collect`), and the Codex runtime directory, including new `worker.py`, `gate-runner.sh` and `gate_runner.py`. Update `scripts/collect.py` and merge the new `templates/config.env` values into project configuration. Preserve project changes and provenance stamps.
- With **independent project hooks**, set `SW_PLUGIN_HOOKS=off` and disable the installed plugin in project `.claude/settings.json`, e.g. `"enabledPlugins":{"sliceworks@engineering-skills":false}`; preserve other entries. Disable the equivalent Codex plugin entry in the project `.codex/config.toml` (`[plugins."sliceworks@sliceworks"] enabled=false`, using the installed marketplace key) if it is also loaded, so copy skills have unique names. Keep independent hooks active. If copied hooks only invoke these package bodies, keep `SW_PLUGIN_HOOKS=on` and disable duplicate plugin loading instead.
- Set `SW_CODEX_BIN=codex` if it is on PATH, or a quoted absolute executable path. On macOS the app bundle can provide `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`; confirm that path exists in the installed app. Missing CLI diagnostics name the configuration key and bundle location.
- A custom dispatcher must keep networking disabled, export the telemetry paths above, record its allocation PID and `thread.started` id immediately, and service gate requests outside the sandbox. Do not widen the writable roots to canonical state. On resume use the sandbox config override, not `-s`. Adapt the verifier's metric paths and confirm slot admission with a real queued gate before rollout.
- Regenerate native profiles with `agents.py sync --root <project>` and run `agents.py check`. The implementer remains process-only; `agents.py show slice-implementer instructions` reads the updated canonical profile directly.

Project-specific Postgres tests, production model dispatch, project hook trust, and the adopting project's custom dispatcher were not exercised by this package release. Automated package tests prove request/result handling, slot-verifier delegation, rejection paths, and telemetry transport using fixture commands; they do not prove a consuming project's SQL gates.
